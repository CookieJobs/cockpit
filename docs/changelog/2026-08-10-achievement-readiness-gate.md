# 2026-08-10 — Achievement Readiness Gate

## 状态

**现行**：完成任务与“可进入多次输出”分离；只有证据充分的成就可为 `ready`。

## 背景

此前完成弹窗默认提交 `cv_status=ready`。当 CV 仍是 `完成「任务标题」` 兜底、结果描述过短，或 AI 已提出但用户尚未回答追问时，成就仍会进入周报、述职、PR 描述和未来 CV 的输出池；同时提醒页只扫描非 `ready`，让这类未完成的数据失去回收入口。

这违背了“完成即沉淀”的质量承诺，也违反 Achievement Distillation Harness 的防御性契约：不明确时应标 `pending` / `needs_data`，而不是假装可用。

## 决策

采用**共享存储边界的确定性质量门**，不依赖 Web UI 或 LLM：

- 调用方请求 `ready` 时，若 CV 仍为标题兜底、outcome 少于 10 个字符、或存在未回答追问，则持久化为 `needs_data`。
- 用户明确选择 `pending` 时保留草稿意图；完成任务始终成功，不以质量门阻塞日常使用。
- 追问必须全部得到非空答案才自动升级为 `ready`；部分回答继续留在补全队列。
- Web、对话工具与 MCP 共用 `storage.complete_task`，因此不会产生入口间状态漂移。

完成弹窗同步说明：待补数据会保存，但不会进入报告；补全后自动可用。

## 不采用

1. **完成时强制补全**：质量高但打断 90 秒沉淀路径，违背低摩擦原则。
2. **仅在报告时过滤**：数据状态仍失真，追问回收链仍断裂。
3. **交给 LLM 决定状态**：`ready` 是输出资格，必须由可审计的程序规则判断。

## 验证

- 新回归覆盖：标题兜底、过短 outcome、未答追问均不能写为 `ready`；部分回答不升级，全部回答后升级。
- 已确认 Web/API/存储定向回归与 TypeScript 类型检查通过。

## 关联

- Lesson #29：输出资格必须在共享写入边界判定，不能由 UI 默认值决定。
- Harness §2.3 / §2.4：不明确时进入人工补全，不进 `ready`。
